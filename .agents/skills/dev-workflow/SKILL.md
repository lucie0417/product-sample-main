# 前端開發與驗證流程

使用者在呼叫此 skill 時會附上前端需求、目標頁面與驗收條件；以該內容為本次需求。

依照本次指令附帶的需求與對話脈絡，執行「需求 → 測試清單 → 開發 → 瀏覽器 MCP 驗證 → 證據交付」。預設使用繁體中文撰寫測試清單及結果。

## 1. 釐清需求與環境

- 閱讀專案指引（`AGENTS.md`）、相關程式碼與既有測試，確認技術棧、啟動方式及本次變更範圍。
- 若缺少會影響實作的需求、驗收條件、測試網址或必要登入方式，先向使用者確認；不得自行猜測重要行為。
- 確認可使用的瀏覽器 MCP（可用 `/mcp` 檢查連接狀態），並依下列順序選擇，後文統稱「瀏覽器 MCP」：
  1. 優先使用 Playwright MCP 的瀏覽器操作及截圖工具。
  2. 若 Playwright MCP 未連接、無法啟動或呼叫失敗，改用 Chrome DevTools MCP（chrome-devtools server）的頁面操作、快照及截圖工具，並在 checklist 的「瀏覽器／視窗」及交付摘要中記錄實際使用的工具與切換原因。
  3. 兩者皆無法使用時，明確回報並請使用者啟用或連接；不得用其他工具冒充，也不得宣稱已完成瀏覽器驗證。
- 僅在使用者授權的本機或測試環境操作；涉及真實付款、刪除資料或其他外部副作用時，先取得確認。

## 2. 開發前先建立測試 checklist

在修改產品程式碼之前，先將測試清單寫入工作區：

- 清單：`docs/dev-workflow/<task-id>/checklist.md`
- 截圖：`docs/dev-workflow/<task-id>/evidence/<run-id>/`
- `<task-id>` 使用日期及簡短功能名稱；若路徑已存在，延用同一任務或選擇不衝突的名稱，不覆寫其他任務。
- `<run-id>` 使用本次驗證的時間戳記，重測時保留舊證據。

清單必須記錄需求摘要、驗收條件、測試環境、前置條件及預定測試案例。每項需求至少對應一個案例，依實際需求涵蓋正常流程、輸入驗證、錯誤流程、邊界情境、載入／空資料狀態、鍵盤操作、響應式版面與相關回歸情境。不要加入與本次需求無關的測試。

每個案例使用唯一編號，寫清楚可重現步驟與可觀察的預期結果。初始狀態全部為未執行，不得預先勾選。採用以下格式，案例數量依需求調整：

```markdown
# <功能名稱> 測試 Checklist

## 需求與驗收條件
- R-01：<需求與可衡量的驗收條件>

## 測試環境
- 網址：<測試網址>
- 啟動方式：<專案既有指令>
- 前置條件：<資料、角色與必要設定，不記錄密碼或權杖>
- 瀏覽器／視窗：<實際使用的瀏覽器與 viewport>

## 測試案例
- [ ] TC-001：<案例名稱>
  - 對應需求：R-01
  - 前置條件：<初始狀態>
  - 操作步驟：
    1. <具體操作>
    2. <具體操作>
  - 預期結果：<可觀察或可量測的結果>
  - 狀態：未執行
  - 實際結果：待驗證
  - 驗證時間：待驗證
  - 證據：待擷取

## 驗證摘要
- 通過：0
- 失敗：0
- 阻塞：0
- 未執行：<案例總數>
- 已知限制：無
```

完成清單後才開始開發。若後續需求改變，先更新清單再修改對應實作，不得為了讓結果通過而降低驗收標準。

## 3. 實作與程式驗證

- 依清單實作需求，沿用既有元件、樣式、架構及專案慣例，避免無關變更。
- 依專案既有工具新增或更新必要的自動化測試，並執行涵蓋本次變更的測試、型別檢查及建置。
- 使用既有啟動方式啟動或連接網站，確認目標網址可回應後，才進入瀏覽器驗證。記錄本次實際環境，不得誤連正式站。

## 4. 使用瀏覽器 MCP 逐項驗證與截圖

- 必須透過瀏覽器 MCP（優先 Playwright MCP，無法啟動時為 Chrome DevTools MCP）實際開啟頁面，依每個案例的步驟執行點擊、輸入、導覽、鍵盤操作及必要的 viewport 調整；單純閱讀程式碼、執行單元測試或擷取靜態頁面不能取代此步驟。
- 每項案例都要從明確的前置狀態開始，使用可辨識的元素定位與條件等待，不以任意延遲取代就緒判斷。
- 逐項比對預期與實際結果，透過頁面內容、DOM／可存取性快照或可用的瀏覽器斷言確認；截圖是佐證，不能單憑截圖檔存在判定通過。
- 每個已執行案例至少保存一張呈現關鍵結果的瀏覽器 MCP 截圖，必要時保存多個步驟。檔名使用 `TC-001-01-<state>.png`，存入本次 `evidence/<run-id>/`。
- 使用工具支援的檔案輸出或複製方式，將截圖實際保存至工作區，確認檔案存在且不是空檔；不得只留下暫存網址或對話中的圖片。若無法持久化，該案例仍未完成證據交付。
- 使用測試資料，避免讓截圖包含密碼、權杖或其他敏感資訊。
- 在 checklist 記錄實際結果、驗證時間、實際 viewport 與截圖相對連結，例如 `[TC-001 截圖](evidence/<run-id>/TC-001-01-success.png)`。
- 只有操作結果符合全部預期、且截圖已保存並連結時，才改為 `[x]` 並標示「通過」。
- 不符合預期時保持 `[ ]`，標示「失敗」，記錄差異及可取得的失敗截圖；修正後透過瀏覽器 MCP 重測，保留先前失敗紀錄與證據，並重跑受影響案例。
- 因工具、登入、資料或環境不足而無法完成時，保持 `[ ]`，標示「阻塞」並記錄原因；尚未操作的案例保持「未執行」。不得將阻塞、跳過或未執行視為通過。

## 5. 交付與完成標準

- 更新 checklist 摘要，確認四種狀態的數量加總等於案例總數，勾選項目與「通過」狀態一致，且所有證據連結均指向存在的檔案。
- 交付簡短摘要：本次實作、checklist 路徑、截圖目錄、程式檢查結果、案例通過／失敗／阻塞／未執行數量及已知限制。
- 全部案例實際通過且證據持久化後，才能宣稱本次流程完成。若有失敗、阻塞或未執行，明確標示未完成與後續必要行動，不得以成功語氣掩蓋限制。
- 不自動提交版本控制；不擅自停止原本已存在的服務，並依使用者需要處理本次啟動的開發服務。
